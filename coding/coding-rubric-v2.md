# 编码规则 v2（可操作版）

用途：供两位编码者逐条判定使用，替代只按类别给默认值的旧规则（v1）。v1 的问题
是把"四类粒度/机制不匹配"的记录一律写成 `Other`，导致 82/121 行机制为 `Other`，
两位编码者在机制上的一致率仅 43.8%（κ=0.29）。

## 0. 判定顺序

每篇按 1→4 的顺序判定。粒度与机制是两个**独立维度**，都必须给出取值。

1. **机制**：文献是否提出或使用下列任一机制来产生一个决策（选精度、选调度、选
   放置、选功耗状态、选代码变换）？——解析模型 / 学习型模型 / 自动搜索 /
   agentic 或 LLM 策略。
2. **粒度**：该机制（或该文献的主要工作）作用的**对象**是计算图、循环与算子、
   设备放置，还是功耗状态？
3. **类别**：按论证功能归入十类之一，冲突时查 §3 的裁决表。
4. **边界**：按该文献在正文中承担的角色判定，见 §4。

## 1. `Other` 的判定

`Other` 是"不适用"，不是"不确定"。只有下列情形才写 `Other`：

- **机制 = Other**：文献既不提出也不使用四类机制。典型：基准与测量方法、纯手工
  库级 kernel 实现、纯数据表示／lowering 基础设施、不面向编译决策的架构级建模。
- **粒度 = Other**：工作对象不落在四类之内。典型：测量方法论、数据集、端到端仿真
  基础设施、体系结构与碳足迹建模。

以下情形**必须**记入具体机制，不得记 `Other`：

| 情形 | 应记 |
|---|---|
| 用贝叶斯／进化／MILP 等做设计空间或调度搜索 | `AutoSearch` |
| 用强化学习或神经网络驱动放置、向量化、精度选择 | `Learned` |
| 用解析式代价模型预测能耗／延迟并据此决策 | `Analytical` |
| 用 LLM／agent 生成或改写代码、选择 pass | `Agentic` |

## 2. 粒度与机制的定义

**粒度**

| 取值 | 定义 | 常见误判 |
|---|---|---|
| `Graph` | 作用对象是计算图：算子融合、图重写、图级重物化、图级精度指派 | 把"用到了图"当作图级优化；只有决策发生在图这一层才算 |
| `Loop/Op` | 作用对象是循环嵌套或单个算子：tiling、调度、内核生成、循环级向量化 | 把只在算子内生效的库调用当作循环级优化 |
| `Placement` | 决定算子/子图/模型在哪一个设备或分区上执行 | 把"跨后端适配"当作放置；必须存在**位置决策** |
| `Power` | 决定频率、电压、功率上限或电源门控状态 | 把"测了功耗"当作功耗状态优化；必须有**状态决策** |
| `Other` | 以上皆不适用 | — |

**机制**

| 取值 | 定义 |
|---|---|
| `Analytical` | 解析式／白盒代价模型或规则化判定 |
| `Learned` | 学习型代价模型、强化学习策略、神经预测器 |
| `AutoSearch` | 以搜索算法（含 ILP、贝叶斯优化、进化算法、自动调优）求解 |
| `Agentic` | LLM／agent 驱动的编译决策 |
| `Other` | 以上皆不适用 |

## 3. 类别裁决表

针对两位编码者实际出现分歧的组合，逐条给出裁决口径：

| 分歧 | 裁决 |
|---|---|
| 建模 vs Pareto | 核心贡献是**代价模型本身** → 建模；核心是**多目标权衡方法或前沿遍历** → Pareto |
| Pareto vs 测量 | 给出权衡方法与前沿遍历 → Pareto；给出测量方法、基准或报告规范 → 测量 |
| Pareto vs 功耗 | 核心是多目标权衡 → Pareto；核心是功耗状态（DVFS／功率上限）编排 → 功耗 |
| 建模 vs 测量 | 提出模型或估计器 → 建模；提出测量方法或对既有测量方法做比较 → 测量 |
| 建模 vs 循环层 | 贡献是可复用的**代价模型** → 建模；贡献是具体的**调度或代码生成系统** → 循环层 |
| 图层 vs Pareto | 在图上做等价变换或重写搜索 → 图层；做多目标权衡 → Pareto |
| 建模 vs AI4C | 贡献是代价模型 → 建模；贡献是学习／LLM 驱动的编译决策方法 → AI4C |
| 建模 vs 稀疏 | 贡献是能耗／性能模型 → 建模；贡献是稀疏性的编译支持 → 稀疏 |

## 4. 边界判据

三者互斥，判据是**该文献在正文中承担什么角色**，与发表年份、技术新旧无关。

| 取值 | 判据 |
|---|---|
| `核心` | 构成某一章节方法论证据的主线，且对象属通用／生产级编译栈或其直接支撑 |
| `桥接` | 为方法学价值纳入，但对象是专用加速器 mapping/DSE、体系结构建模或测量基础设施，不属通用编译栈；或仅部分落在本文范围 |
| `前沿` | 仅作趋势观察或窗口外补充，未进入任何章节的方法论论证 |

常见误判：把"新发表"当作前沿（应以角色而非年份判定）；把"对象是专用加速器"当作
核心（应记桥接）；把用于界定生态的框架文档记入边界（其不属统计样本）。

## 5. 校准流程

1. 打开 `calibration-sheet.csv`，其中列出两轮编码在四个字段上的全部分歧；
2. 逐条判定并填写 `agreed` 列；每条一致的裁决理由写进 `note`；
3. 若某条新规则被反复用到，先补进本文件再继续；
4. 校准完成后按 v2 规则全量重编，运行
   `python repro/compute_kappa_two_coder.py` 重算 κ；
5. 目标：四个字段的 κ 均不低于 0.6。未达标时，重复第 1–3 步。

## 6. 与旧版的关系

v1 报出的"类别 κ=0.87、边界 κ=0.79"在独立复核下未能复现（实测类别 κ=0.706、
边界 κ=0.258）。v2 起，正文只报告可复现的一致性数值，并如实说明编码轮次与规则修订。
